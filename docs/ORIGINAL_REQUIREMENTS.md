## 一、作业背景与要求

老师的核心要求如下：

1. 基于 RBAC（Role-Based Access Control）原理设计权限系统。
2. 使用监听器模式和事件响应机制实现应用程序中的用户操作。
3. 提交完整的代码实现。
4. 提供页面操作展示和角色、权限控制效果。
5. 分析 RBAC 权限控制机制，重点说明页面、菜单、功能按钮之间的控制异同。
6. 所有实际角色授权关系及权限定义必须保存在数据库表中，不能在源代码或页面中硬编码用户的权限。
7. 扩展分析 RBAC0、RBAC1、RBAC2、RBAC3 模型。

老师尤其强调：同一个页面，不同用户应该拥有不同的操作能力；系统中的用户、角色、权限模块应具有可复用性，适合未来移植到其他管理系统。

## 二、项目目标

项目名称：Campus Work Order RBAC System

中文名称：基于 RBAC 的校园工单管理系统

请开发一个真实可交互的桌面管理程序。它包括工单业务模块和独立的 RBAC 权限模块。

最重要的用户体验是：

- 不同账号登录同一个应用。
- 不同角色看到不同的菜单或页面。
- 在同一个工单管理界面中，不同用户拥有不同的按钮操作权限。
- 管理员可以在可视化管理界面中分配角色和权限。
- 权限修改保存到数据库后，重新登录或者刷新权限即可生效。
- 真正的业务操作由事件监听器触发。
- 即使绕过 UI 直接调用业务服务，也无法越权执行操作。

请优先保证以上功能完整、正确、可验证。

## 四、软件架构

建议拆分为：

- UI 层：登录、主窗口、工作台、工单列表、用户管理、角色管理、权限配置、审计日志。
- Event 层：事件监听器及界面事件处理逻辑。
- Service 层：认证服务、权限检查服务、用户服务、角色服务、工单服务。
- Repository/DAO 层：数据库访问和数据持久化。
- Model 层：用户、角色、权限、工单等实体。
- Infrastructure 层：数据库初始化、事务、日志、异常处理。

要求 UI 与核心 RBAC 逻辑解耦。

## 五、数据库

至少包含以下表：

- users
- roles
- permissions
- user_roles
- role_permissions
- work_orders
- audit_logs

根据需要可适度增加表和索引。

数据库需要满足：

1. 体现 User、Role、Permission 之间的多对多关系。
2. 一个用户可以拥有多个角色。
3. 角色可以具有多个权限。
4. 不同角色可以共享权限。
5. 用户有效权限等于其角色权限的并集，默认拒绝未授予权限的操作。
6. 权限表具有唯一的 permission_code，明确标注 PAGE、MENU、ACTION 等资源类型。
7. 数据表使用必要的主键、外键、唯一约束和索引。
8. 启用 SQLite 外键约束。
9. 所有数据库操作使用参数化查询，避免 SQL 注入。
10. 重要的多表授权操作使用事务。
11. 保存用户密码的安全哈希，不存储明文密码。
12. 支持数据库自动初始化和初始数据填充。
13. 初始化必须具有幂等性，重新运行不能覆盖正常业务数据或重置管理员做出的权限修改。
14. 数据库文件在程序重启后继续保留。
15. 交付 schema.sql、seed.sql，并说明数据库文件位置和如何查看授权表。

可以在代码中定义稳定的权限编码常量，但绝不能硬编码角色拥有的权限或者根据用户名直接判断管理员身份。

## 九、事件监听器实现

必须明确使用 Java Swing 的事件监听机制。

至少让以下操作具有真实事件处理逻辑：

- 登录按钮点击
- 菜单点击

- 工单编辑
- 工单删除
- 角色分配
- 角色权限更新

示例流程：

用户操作 -> ActionListener -> 业务 Service -> PermissionService 校验 -> Repository -> 数据库 -> 操作结果 -> UI 更新。

每一个影响数据的业务操作必须在 Service 层重新判断权限，不能只通过 UI 禁用按钮完成安全控制。

请保留明确的事件监听代码，以便老师检查。

## 十、权限安全与一致性

重点满足：

1. 权限默认拒绝。
2. 不允许通过直接调用 Service 绕过检查。
3. 不通过用户名字符串授予权限。
4. 修改角色授权后能重新从数据库获得有效权限。
5. 避免陈旧缓存造成权限被撤销后仍然可以执行操作。
6. 多角色用户采用权限并集。
7. 非管理员不能修改角色授权。
8. 禁止普通用户通过参数伪造管理员身份。
9. 禁止普通用户直接删除其他用户、修改角色或分配权限。
10. 禁止删除最后一个有效系统管理员或使系统进入无法管理权限的状态。
11. 成功和被拒绝的关键操作应记录审计日志。
12. 权限拒绝应产生可解释的错误信息，程序不能直接崩溃。

- 如何验证数据库权限配置。
- 测试是否真实通过。
- 具体执行过哪些构建与测试命令。
- 是否存在环境限制或已知问题。
- 是否还有需要我手工完成的事情。

不要为了按时结束而掩盖失败。优先修复影响启动、授权、安全或核心演示的问题。
