# RBAC 模型分析补充

## 1. 已实现的 RBAC0 与 RBAC1

本系统的 RBAC0 由 `users`、`roles`、`permissions`、`user_roles` 和 `role_permissions` 构成。用户可拥有多个角色，角色可拥有多个权限；每次 Service 调用从可信会话令牌解析用户，并按数据库当前角色权限的并集授权。菜单、页面和按钮只负责展示差异，`Access.read/write` 才是最终安全边界。

RBAC1 新增 `role_hierarchy(senior_role_id, junior_role_id)`。`senior -> junior` 表示高级角色继承低级角色的有效权限，例如 `MANAGER -> STAFF`。递归 CTE 从用户直接角色向下遍历所有可达角色，再以 `DISTINCT` 得到有效权限。角色页显示直接、继承、直接加继承三种来源；关系初始为空，不改变原有 RBAC0 演示账号。

层次关系用联合主键、外键级联删除和自身继承检查保护。服务层拒绝重复边与环；每次层次修改在 SQLite 写事务中完成授权、关系写入、最后有效管理员校验和审计。`RoleHierarchyTest` 已验证多层继承、来源去重、动态撤销、循环、删除清理和版本 1 到 2 的持久化迁移。

## 2. RBAC2：约束模型（理论分析）

RBAC2 在 RBAC0 上加入约束。静态职责分离（SSD）阻止用户同时被分配冲突角色，例如“设备报修提交人”和“报修审批人”；动态职责分离（DSD）允许用户拥有多个角色，却禁止同一会话同时激活冲突角色。其他常见约束包括角色人数上限、角色前置条件、用户可拥有角色数量上限。

若将 RBAC2 扩展到本项目，可设计 `role_conflicts(role_a_id, role_b_id)`、`role_constraints` 与会话激活角色表，并在 `Users.setRoles`、登录和切换活动角色时校验。该设计会影响业务规则和界面，因此本项目未将其作为已交付功能。

## 3. RBAC3：层次与约束的组合（理论分析）

RBAC3 同时包含 RBAC1 层次和 RBAC2 约束。此时约束必须针对递归后的有效角色集合，而不能只检查直接分配。例如 A 继承 B，B 与 C 互斥；给用户分配 A 和 C 时，系统也应识别间接得到的 B 与 C 的冲突。实现需要在层次变更、角色分配和会话激活时运行递归冲突检测，并定义冲突时的回滚和审计策略。

| 模型 | 关键对象 | 本项目状态 |
|---|---|---|
| RBAC0 | 用户、角色、权限、UA、PA | 已实现 |
| RBAC1 | 角色层次 RH、递归继承 | 已实现 |
| RBAC2 | SSD、DSD、互斥/基数等约束 | 仅理论分析 |
| RBAC3 | RBAC1 与 RBAC2 的联合 | 仅理论分析 |

RBAC2、RBAC3 说明了未来可能的设计方向，不应误写为当前程序功能。
