# RBAC 模型分析

## 本项目的 RBAC1 实现

系统在既有 RBAC0 的用户—角色（`user_roles`）和角色—权限（`role_permissions`）关系上增加 `role_hierarchy`。一条 `(senior_role_id, junior_role_id)` 记录表示高级角色继承低级角色的全部有效权限；一个用户持有高级角色时，拥有该角色、其全部直接下级和间接下级角色的权限并集。

关系为空是初始状态，因此升级后不会改变 ADMIN、MANAGER、STAFF、VIEWER 的原有权限。关系由管理员在角色页面配置，不能由用户名或角色名称获得特殊放行。

## 约束与安全性

- 表以 `(senior_role_id, junior_role_id)` 为主键，两个外键均为 `ON DELETE CASCADE`，避免悬挂关系。
- 数据库 `CHECK` 拒绝自身继承；服务层的递归可达性检查拒绝环和重复关系。
- 角色继承的增加、删除和批量替换要求 `role:manage` 与 `permission:grant`，均在 SQLite 写事务中授权、修改、审计。
- 每次 Service 调用重新查询数据库的递归有效权限；旧会话在层次或权限被撤销后的下一次调用立即失效。
- 删除角色、替换直接权限或层次关系时，都会检查至少保留一个具备用户管理、角色管理、授权和角色页面入口能力的有效用户。

## RBAC0—RBAC3

| 模型 | 定义 | 本项目处理 |
|---|---|---|
| RBAC0 | 用户、角色、权限与两个多对多分配关系 | 已实现，保留原有行为 |
| RBAC1 | 增加角色层次与权限继承 | 已实现，支持多层、并集、来源显示和动态撤销 |
| RBAC2 | 增加职责分离、互斥角色、会话激活集合等约束 | 未实现；课程范围未要求 |
| RBAC3 | RBAC1 和 RBAC2 的组合 | 未实现；不能把层次关系当成职责分离 |

## 控制层次

菜单、页面和按钮用于使能力差异可见：无菜单权限不显示入口、无页面权限不可导航、无操作权限按钮禁用。它们不是最终安全边界。`Access` 在服务调用中从可信令牌取得操作人，再基于当前 SQLite 数据计算有效权限；即使直接调用 Service，也不能绕过这一检查。
